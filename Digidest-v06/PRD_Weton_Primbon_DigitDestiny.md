## 2. What it is

The Javanese calendar overlays a 7-day week (*saptawara*) with a 5-day market cycle (*pasaran*: Legi, Pahing, Pon, Wage, Kliwon). Their intersection for any date is a **weton** (35 possible combinations). Each day and pasaran has a fixed numeric weight (**neptu**); weton neptu = weekday value + pasaran value. This is core to Javanese/Indonesian primbon tradition: birth character reading, marriage-date selection, and — most commonly searched — **couple compatibility (jodoh)**.

### Confirmed reference data (cross-checked across independent sources)

| Weekday | Neptu |
|---|---|
| Sunday (Minggu) | 5 |
| Monday (Senin) | 4 |
| Tuesday (Selasa) | 3 |
| Wednesday (Rabu) | 7 |
| Thursday (Kamis) | 8 |
| Friday (Jumat) | 6 |
| Saturday (Sabtu) | 9 |

| Pasaran | Neptu |
|---|---|
| Legi | 5 |
| Pahing | 9 |
| Pon | 7 |
| Wage | 4 |
| Kliwon | 8 |

**Formula:** `Neptu Weton = Weekday Neptu + Pasaran Neptu`
Example: Friday Kliwon = 6 + 8 = 14.

**Compatibility (jodoh):** Sum both partners' neptu weton, then map via a modulo-8 lookup to one of 8 traditional categories: Pegat, Ratu, Jodoh, Topo, Tinari, Padu, Sujanan, Pesthi. (Exact modulo bucket boundaries need one more verification pass against a primary primbon text before launch — see Open Questions.)

## 3. AI trust boundary (same discipline as Quran tool)

- **Deterministic, no AI:** date → weekday → pasaran → neptu → weton name → compatibility category. Pure calculation, zero hallucination risk, 100% reproducible.
- **AI-assisted, bounded:** narrative interpretation text (character description, compatibility explanation, "good day" guidance) generated by DeepSeek V4 Flash *from a fixed reference table of category meanings*, not freely generated. Prompt constrains the model to elaborate on the given category (e.g. "Pesthi: harmony and stability") rather than invent new claims.
- Add a standard disclaimer surfaced in-app (matches how existing weton tools frame it): *cultural reflection, not fate/prediction*. This is standard practice across all reference sites reviewed and reduces liability exposure.

## 4. Scope — MVP

**In scope:**
1. **Individual Weton Lookup** — input birth date → output weekday, pasaran, neptu, weton name, short AI-generated character reflection.
2. **Couple Compatibility (Jodoh)** — input two birth dates → combined neptu → category (Pegat/Ratu/Jodoh/etc.) → AI-generated relationship reflection text.
3. **Bilingual EN/ID** toggle, consistent with existing Digit Destiny pattern.
4. **Telegram bot command** (`/weton [date]`, `/jodoh [date1] [date2]`) — consistent with @DigitDestinyBot pattern already in place.
5. **Wuku/Pawukon 30-day cycle layer** — adds the 30-wuku Pawukon reading as an additional output layer alongside weton/neptu. Requires its own verified lookup table (30 wuku names + associated meanings) and a second cycle-epoch calculation independent of the pasaran epoch.
6. **"Good day" (*petungan*) selection for weddings/events** — rule-based recommendation engine matching event type against weton/pasaran combinations and traditional avoid-days. This is a genuinely different feature shape from the lookup/compatibility tools above (multi-factor rule matching vs. single lookup+sum), and needs its own primary-source verification of the rule set before build.
7. **Maghrib-boundary day-change handling** — for births/events near sunset, determine Javanese calendar day using local Maghrib time (Asia/Jakarta or location-aware) rather than midnight, per the traditional convention.

**Note on scope:** items 5–7 were originally scoped for v2 given their added technical/verification surface (see Section 6, Risks). Moved into MVP per direction — see Section 6 for the corresponding risk additions this introduces.

## 6. Risks / open questions (mentor's honest list)

1. **Pasaran epoch calculation is the one real technical risk** — everything else is a lookup table, but converting Gregorian date → pasaran position requires getting the cycle anchor right. Verify against 3+ known reference dates before trusting any formula, including ones sourced in this PRD's research pass.
2. **Compatibility category boundaries need primary-source verification** — the modulo-8 buckets (Pegat/Ratu/Jodoh/etc.) appeared consistent across sources checked, but "traditional" systems often have regional variation. Cross-check against at least one Indonesian-language primbon reference before shipping, not just English secondary sources.
3. **This is still a low-monetization feature** — it strengthens Digit Destiny's content depth and SEO surface (Indonesian keyword space is genuinely under-served in English/bilingual form) but by itself isn't a revenue driver. Treat it as a distribution/SEO play, not a new business line — consistent with your existing portfolio problem of building over monetizing.
4. **No confirmed link to @neuralmelodies audience yet** — the "distribution synergy" argument is plausible, not proven. Don't count on it in any success metric until you've actually tested a cross-promotion.
5. **Wuku epoch is a second unverified calculation, independent of pasaran** — same category of risk as item 1, but doubled. Both epochs need verification against known reference dates before either ships; do not assume the pasaran verification pass covers wuku.
6. **Petungan rule set has no single authoritative source** — unlike neptu/pasaran (consistent across every source checked), "good day" rules vary meaningfully by region and primbon text. Pick one authoritative reference (e.g. a specific published Primbon text) and document it explicitly in-app, rather than blending sources — blended rules will produce results a knowledgeable user can immediately spot as inconsistent.
7. **Maghrib-boundary logic requires a location/timezone decision** — "local Maghrib time" isn't a fixed clock time; it needs either a fixed Asia/Jakarta approximation (simpler, less accurate for users elsewhere) or an actual sunset-time calculation (more accurate, more engineering). Decide and document which before building, rather than discovering the ambiguity mid-implementation.
8. **Combined effect on timeline:** items 5–7 roughly double the pre-build verification workload described in Section 6 item 1–2. If timeline matters, consider sequencing (ship weton+jodoh first, wuku/petungan/maghrib as fast-follow) even though all four are formally "MVP" now — a partial ship beats a delayed complete one.

**Rationale:** This page does double duty — it's a differentiator (most competing weton/numerology apps don't disclose their AI/data boundary at all) and a defensible answer if the AI-generated content is ever questioned, since it documents the constrained-narrative-only design decision made in this PRD rather than leaving it implicit in code.
